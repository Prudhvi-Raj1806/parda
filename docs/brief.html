Secret Wards: an offline privacy firewall for hospital records

Yugaantar 2026 · DevForge, Track 3 · Team: Prudhvi (lead), Prahlad, Sanskar · Repository: github.com/Prudhvi-Raj1806/devforge-secret-wards

1. What we built and why it is different

A single command reads a messy folder of hospital exports (CSV, TSV in UTF-16 or cp1252, nested JSON, FHIR bundles, text notes, base64 attachments) and writes a sanitised copy, a report and a record map. It uses only the Python standard library, runs offline, and never calls a model. What is distinctive: the pipeline learns the names and addresses in the dataset first, then removes every occurrence in every channel, including file names, JSON keys, headers, metadata and base64. It links a patient across files only on identifiers that identify one person, so two people who share a name are never merged.

3. Ingestion and detection

  • Formats. CSV and TSV keep their delimiter and header; JSON keeps its structure; text notes are cleaned as text. FHIR bundles keep their JSON shape. Anything else is quarantined with the reason and no content.
  • Structured fields. A column or key is classified by its name (English and romanised Hindi: Naam, Pita ka Naam, Janm Tithi, Pata, Jila) and replaced whole when it holds a name, ID, phone, address or date. Medical columns are never matched.
  • Free text. Labelled and relative names, honorifics, and candidates next to a phone or contact cue. Devanagari names are found after नाम: and next to phone numbers. Medicine names are never names: generic-drug endings (-pril, -statin, -mycin) and clinical words are rejected. Dr. names stay.
  • Identifier shapes. Aadhaar (plain and masked), ABHA, PAN, e-mail, hospital numbers, insurance IDs, and 10-digit mobiles in Latin and Devanagari digits.

4. Linking and pseudonyms

Two records are linked only by a shared strong identifier: Aadhaar, ABHA, PAN, e-mail, insurance ID, a hospital number, or a mobile number. A name, a village or a doctor is never enough. A record that names two different patients (a ward sheet, a helpdesk ticket) links nothing. Each cluster gets a pseudonym HMAC-SHA256(RAKSHA_SECRET, smallest key), written into the patient's name field, so the same person gets the same ID in every file. Plain hashes are not used: they can be reversed by someone holding a voter list.

5. Privacy layer and the trade-off

Patient and relative namesPseudonym for linked patients, otherwise [PATIENT_NAME]; [RELATIVE_NAME]Names are direct identifiers

Trade-off. Shifting dates and banding ages costs a little precision for a researcher (ages become ranges, dates move), but a stay of nine days is still nine days. Removing villages and PINs costs geographic detail, which matters less than the risk of singling someone out in a small village.

6. Security design

  • The secret comes from the environment and is never written. The run refuses to start without it.
  • Stdout and logs show counts only. Errors show the exception class and the input hash, never content.
  • No temporary files. The registry and the linker live in memory and are discarded when the run ends.
  • Unparseable files are quarantined, never copied. File names that collide after scrubbing get a suffix from the input hash, so no file is overwritten.
  • Deterministic: the same input and secret produce byte-identical output; a different secret changes every pseudonym and shift.

Measured on the practice data with the kit's checker, using a local copy of that checker that matches files on disk (172 of 200 hashes in the answer key do not match the files on disk). These are rough guides, not the official score.

Known limitations. (1) Column rules recognise common headers; an unfamiliar header falls back to text rules, so address columns can leak. (2) A name with no label, no honorific and no phone nearby is missed, for example a bare first name in a note. (3) Dates in unfamiliar formats are not shifted. (4) FHIR is kept as the same JSON structure but is not validated against R4. (5) The hospital ward is kept as medical context, so a ward number in an address can leak. (6) The rules were tuned on practice data; the header-rename test is our best estimate of how they transfer. (7) No real data was used at any point.
